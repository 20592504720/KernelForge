## 2. Dual source acquisition design (preparatory task COMPLETE)

The canonical identity remains manifests/oneplus13-pjz110-sm8750-source.lock.json with the already fixed 35 project Commit SHAs and exact official manifest Commit. Do not rewrite these identities for an optimization.

- **Strategy repo-git-lock-v1:** existing Repo workspace and verifier. Requires real Git objects, exact 35 matching HEADs, verified manifest and fully materialized declared files; emits source_sync=TESTED only on success. Preserve .repo for interrupted resume, and do not change the running workspace.
- **Strategy pinned-archive-v1 (future):** opt-in immutable archive per project when the provider supports the exact pinned revision. Metadata should include repository URL, manifest project/path/revision, canonical Commit SHA, verified archive SHA256, expected extracted-tree identity, archive provider/format, fetch URL and safe extraction outcome. An archive checksum verifies archive bytes, **not automatically the Git Commit**. An independently trusted binding between archive bytes/tree and the pinned Git tree is required before declaring SOURCE_CONTENT_VERIFIED.
- No provider fallback may silently replace a locked Commit with a branch tip or a different mirror snapshot. Record a missing or inaccessible archive as BLOCKED; fall back to locked Git only when the same identity can be verified.
- Preserve executable bits, symlinks, ownership-neutral extraction, manifest linkfile/copyfile behavior, subproject mounts and deterministic project ordering. Reject traversal, absolute paths, escaping symlinks/hardlinks, special files, collisions, overlapping projects (except separately reviewed "./" root semantics), symlink destinations and untrusted network redirects.
- Store a separate acquisition report, e.g. source-acquisition-report.json, with strategy, lock digest, per-project evidence, byte counts and failure stage. Do not reuse the Repo verifier's 35/35 Git HEAD status for archive fetches.
- **Patch boundary:** the kernel common source and any other patch target must remain in a real verified Git checkout, so existing apply_series() and SUSFS integration remain valid. Archive substitution for a patch target is explicitly blocked until equivalent ancestry/transaction semantics are implemented and tested, not simply simulated with git init.
- If build inputs can be reduced, prove via dependency graph and exact-target build checks that all required OKI files, rules, toolchains and vendor modules are present. A fast GKI-only Image is not a 35-project OKI build.

Required future tests: pinned vs moved branch; historical Commit not available via shallow fetch; archive tamper/corrupt/truncated; missing CodeLinaro historical archive; 35 path mapping including "./"; duplicate paths and project collision; malicious tar symlink/hardlink/mode; manifest linkfile/copyfile crossing boundaries; archive-vs-Git content comparison with file modes; patch series against Git versus rejected archive; host filesystem differences; negative and positive provenance reports.

## 3. GitHub Releases toolchain mirror design (preparatory task COMPLETE)

Reference designs: [Hipuu OnePlus13 source-sync action](https://github.com/Hipuu/OnePlus13-KernelBuilder/blob/main/.github/actions/kernel-source-sync/action.yml) uses per-Manifest source archives and CodeLinaro concurrency control; [LingLuo17 toolchain mirror workflow](https://github.com/LingLuo17/OnePlus_KernelSU_SUSFS/blob/main/.github/workflows/mirror-toolchains.yml) mirrors pinned large archives to Releases. These are design precedents, not evidence that our locked 35-project OKI build will fit a hosted runner. Do not copy unreviewed shell downloads, broad deletion steps or an upstream cache blindly.

- Add a source-adapter/mirror resolver in the **existing** ToolchainManager. The primary identity is toolchain kind, pinned upstream repository/Commit or verified release identity, host and target architecture, version, binary layout, expected trusted SHA256 and adapter version. Mirror metadata links Release asset bytes to that identity.
- First resolve against an existing verified local/cache entry **within the current runner**; then a compatible trusted GitHub Release asset; then the original pinned upstream source if available. Every fetch must pass the expected SHA256 before extraction; an upstream re-packed archive with different bytes requires a separately audited lock and cannot be accepted as a transparent replacement.
- Release tag and asset filename are mutable identifiers, not security proofs. Verify digest from a reviewed lock, record uploader/asset identity and origin; deny ambiguous split parts, missing parts, noncontiguous part indices, incorrect combined digest, or size/host-arch mismatches. Respect GitHub Release asset size/permissions/rate limits and verify those quotas before publication.
- Preserve ToolchainManager's atomically installed cache, portable FileLock, cache metadata, leases and its three acquisition modes. Do not introduce a parallel manager or overwrite user-supplied existing caches. For Rust/build-tools and vendor-specific prebuilts, first define a separate verified resource class or explicitly extend schemas + validation; the current LLVM/GCC manager cannot be assumed to accept arbitrary Rust tarballs.
- Do not publish vendor-proprietary or non-redistributable binary/toolchain assets without checking license and permissions. No credentials in logs; GitHub Actions token permissions should be read-only for build and narrowly scoped to contents:write only for a separate authorized mirror-publishing job.
- Hash and validate the final installed tree and tool executable version/architecture. A hash-correct archive with an unusable LLVM layout is a failure, not TESTED.

Future negative tests: malicious archive; wrong SHA256; part missing/duplicated/reordered; unsigned/unapproved replacement at same Release tag; unexpected compiler version; unsupported host architecture; failed mirror and pinned origin fallback; concurrent same-cache attempts; interrupted publish/install; stale cache and lease conflict; permission-denied publication.

## 4. GitHub Actions cache and runner-capacity plan (preparatory task COMPLETE)

- Separate workflows: **lightweight validate/manifest** (regular PR), **toolchain mirror maintenance** (manual and narrowly scoped), **fast kernel compile** (manual and dependency-verified), **full official OKI** (manual one-attempt, admission gated), and **release** (guarded by evidence). Existing Stage 5 sync and current preflight build workflow remain unchanged.
- Cache layers must be distinct: source archives / immutable toolchain assets in reviewed Release storage where useful; small reusable compiler output in bounded ccache; Bazel repository/output-cache policy to be measured rather than assuming it fits. Do not put full 35-project Git worktrees inside actions/cache, and do not rely on caches surviving eviction.
- ccache key/isolation must reflect device profile + kernel/manifest lock digest + compiler SHA/version + Root provider/Commit + SUSFS and patch lock digest + effective .config/build target + architecture + relevant build switches. Cross-device, cross-compiler and incompatible patch variants must not share a writable cache. A cache hit is performance evidence only, never source integrity or compilation acceptance.
- GitHub-hosted runners are ephemeral; a previous run's source files do not persist. Pin third-party Actions to reviewed full SHA. Respect read-only default token for untrusted PRs; do not execute arbitrary PR scripts with Release write permissions.
- Stage 5 hosted Run 44991299785 matched 31/35 before timeout and consumed ~80 GiB on its ephemeral runner. This is **not** evidence of a successful 35-project or full Bazel build. The earlier .NET cleanup disk pilot recovered ~6.3 GiB, not enough to claim full OKI fits. The user's WSL ext4 volume may advertise virtual free space much larger than physical E: free capacity; the current separate E: guard remains essential.
- Every large Actions job must sample physical workspace/temp free bytes and inodes before admission, after acquisition, before/after compilation, and on failure; publish peak usage, phase, timings, bytes transferred where measured, per-project sizes, exit reasons and an Artifact report. Use a measured margin from the Stage 5 completed workspace and **additional** build-output peak. Avoid invented universal disk quotas and destructive cleanup.
- Optimize only after measurement: compare --depth=1/partial Git checkout, archive extraction and necessary-subset approaches with the same pinned identities. Reduce disk duplication (Git objects + extraction + Bazel outputs + mirrored archives) but never discard required kernel/vendor inputs. CodeLinaro should use limited concurrency and bounded retry/fallback; unlimited parallel download can cause truncation or throttling.
- Fail closed with explicit BLOCKED_RESOURCE, BLOCKED_PROVENANCE, BLOCKED_DEPENDENCY, TIMEOUT or TEST_FAILED; never silently select fast mode after full mode was requested. A hosted runner with insufficient measured disk is a blocker; larger paid hardware or persistent self-hosted servers require separate user authorization.
- Incremental optimization acceptance measures both **network bytes** and **peak disk bytes** plus wall-clock time; those measures are different. Cloud caching must not make a personal Windows/WSL computer an ongoing runner.

Future tests: cache key collision/poisoning, stale key restore, corrupt entry recovery, toolchain cache race, disk threshold just above/below reserve, inode exhaustion, runner shutdown, Git host 429/5xx, bounded CodeLinaro concurrency, smoke checks for Node 24 Actions, secret redaction, read-only PR, release publishing permissions and Artifact hash validation.

## 5. Stage 6–9 implementation sequence and acceptance contracts (preparatory task COMPLETE)

This **replaces the forward-looking numbering** formerly used for Stage 6 generic features and Stage 7 devices/delivery in docs/ROADMAP.md; it does **not** remove those feature/device obligations. The old Stage 6 feature concerns move into Stage 6 compatibility groundwork and Stage 7 feature build tests; old Stage 7 device/delivery concerns move into Stages 8 and 9. The protected Stage 5 gates are not waived by a renumbering.

### Stage 6 — acquisition strategies and integration compatibility

Implement opt-in dual acquisition and versioned source workspace/provenance contracts, with safe archive extraction and stable Git-backed patch targets. Resolve manifest link/copy/root layout; preserve patch series lock/rollback. Review BBG missing source headers, Unicode semantics/licensing and Fengchi provenance before any integration. **Gate:** static/schema/fixture tests including all negative cases, verified per-project Commit/content evidence on a small real fixture plus targeted actual OnePlus subset (not 35-project rerun). Existing Stage 5 Git path must remain passing. Full fast/full OKI parity stays UNTESTED until built.

### Stage 7 — mirror and cache integrations, first real fast build

Extend ToolchainManager for reviewed mirror assets; implement verified non-LLVM resource handling where required; bound ccache and cache keys; add a manual-only fast-build Actions workflow. Add Root/SUSFS and networking/ZRAM per-feature builds only where exact baseline permits. **Gate:** checksum, corrupted cache, concurrency, arch/version and license checks; at least one real pinned OnePlus 13 fast-source Image and vmlinux build in Actions with source, compiler, config and artifact hashes. A fast image does not claim Vendor Modules, DTBO, KMI/ABI or boot. An optimization setting cannot suppress KCFI or ABI enforcement merely to get green.

### Stage 8 — full official 35-project OKI build and device evidence

Add a multi-project workspace provider for exact official manifest lock and a reviewed Kleaf/Bazel sun target; verify vendor modules, device tree, DTBO and KMI/ABI against actual firmware context. Measure total workspace/Bazel output/cache peak on an authorized runner before compilation. **Gate:** 35/35 Git or independently equivalent pinned-content proof; exact target, compiler and inputs; nonempty Image/vmlinux and required module/device artifacts with hashes; compile logs and ABI evidence. Missing licenses, firmware, signing keys, artifacts, KMI or capacity are explicit BLOCKED/UNTESTED, never green. No actual boot claim without device evidence.

### Stage 9 — stable Actions interface, reproducibility and guarded publication

Expose checked device/root/patch/source-mode choices via manual workflow inputs; enforce incompatible combo exclusions; publish compact evidence/artifacts; release only if artifact provenance, firmware/ABI/boot policy and package validation pass. Never auto-upload flash-ready images based solely on a successful Image build. **Gate:** representative matrix and negative combinations, fast/full mode isolation, cold/warm cache reproducibility and invalidation, interrupted mirror/download recovery, release permission gates, Artifact checksum/re-download verification and documented rollback. Manual device boot/Root validation remains separately attributed to real evidence.

**Current completion state:** Stage 5 pending actual 35-project sync outcome and its existing remaining gates; Stages 6–9 = DESIGN_ONLY, no workflow/build/boot execution. This document creates no automatic transition.
